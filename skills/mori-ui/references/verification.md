# Mori UI 検証手順

## 目次

1. 変更範囲を固定する
2. 静的監査
3. プロジェクト検証
4. 実画面を開く
5. 状態を巡回する
6. 操作性とアクセシビリティ
7. 回帰確認
8. 最終報告

## 1. 変更範囲を固定する

実装前後で次を記録する。

- 対象ページと主要フロー
- ロゴ、ファビコン、ナビゲーション
- 主要アクションとショートカット
- 既存の読込中、空、エラー、成功状態
- 対象外のページと機能

依頼されていない機能削除を、視覚整理として扱わない。

## 2. 静的監査

対象ルートで監査スクリプトを実行する。

```powershell
uv run --no-project python <skill-dir>\scripts\audit_ui_slop.py <ui-root>
```

重大度の目安:

- `high`: 意図せず残すと画面全体をテンプレ化する表現
- `medium`: 反復時にテンプレ感を強める表現
- `low`: 人による確認を促す小さな兆候

結果ごとに「削除」「題材に合う形へ変更」「理由があるため維持」を決める。ゼロ件だけを成功条件にしない。

## 3. プロジェクト検証

リポジトリが定めるコマンドを優先し、該当するものを実行する。

- formatter
- lint
- 型検査
- 単体・結合テスト
- production build

警告や既存失敗を新規失敗と混同しない。実行したコマンド、結果、未実施理由を残す。

## 4. 実画面を開く

可能なら実際の開発サーバーを起動し、DOMだけでなくレンダリング結果を確認する。

代表的な幅:

- 320〜390px: 小型モバイル
- 768px前後: タブレットまたは狭いウィンドウ
- 1440px前後: デスクトップ

スクリーンショットでは次を見る。

1. 3秒で主役と主操作を指差せるか
2. 切れ、重なり、不要な横スクロールがないか
3. 固定UIがコンテンツを覆わないか
4. 見出しと本文の行長が破綻していないか
5. 同じ角丸カードが画面を占領していないか
6. 題材固有の語彙・形・操作が見えるか
7. 装飾を説明できるか
8. 各テキストが判断、操作、識別、現在地の理解のいずれかに役立つか

英語キッカー、章番号、副題、小ラベルを一度非表示にしても理解が変わらないなら、原則として削る。実際の手順番号、識別子、単位、ブランド名はこの確認だけで削除しない。

## 5. 状態を巡回する

主要フローで次を可能な範囲で表示する。

- 初期状態
- 入力中または選択中
- 読込中
- 成功
- 空状態
- バリデーションエラー
- 通信・処理エラー
- 無効状態

色だけに依存せず、文言、アイコン、位置を組み合わせる。エラーには回復操作を置く。

## 6. 操作性とアクセシビリティ

- Tab順が視覚順と一致する
- フォーカスリングが見える
- アイコンボタンにアクセシブルな名前がある
- ラベルと入力が関連付く
- コントラストが読み取りに十分
- タッチ対象が密集しすぎない
- ズームや文字拡大で主要操作が失われない
- `prefers-reduced-motion` で不要な動きが止まる
- ホバーだけに情報を隠さない

## 7. 回帰確認

変更前に存在した次を再確認する。

- ページ遷移
- 保存、削除、戻る、取消
- 検索、フィルター、ソート
- キーボードショートカット
- 認証状態に応じた表示
- URLやブラウザ戻るとの整合
- ロゴ、ファビコン、タイトル

## 8. 最終報告

次を簡潔に伝える。

- Design Readと採用した視覚モチーフ
- 消したAI既定表現
- 理由があって残した例外
- 実行した検証
- 確認した画面幅と状態
- 残る制約や未確認事項
